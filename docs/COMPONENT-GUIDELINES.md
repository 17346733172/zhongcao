# 组件开发、样式、依赖和无障碍规范

状态：Next.js 16、React 19、TypeScript 前端实施规范。最后更新：2026-10-26。

## 1. 组件分层

| 类型 | 职责 | 示例（不是现有文件） |
| --- | --- | --- |
| 基础控件 | 通用输入、操作和反馈 | Button、Input、Badge |
| 布局组件 | 页面结构与区域排列 | Header、Sidebar、Container |
| 业务组件 | 表达具体业务流程 | 根据产品范围确定 |
| 示例组件 | 展示组件行为与使用方式 | 仅组件站需要 |
| 页面容器 | 组织页面与数据状态 | 根据路由确定 |

只有出现明确复用需求时才抽取通用组件，避免为了分类预建空文件。

## 2. 命名和接口

- 命名使用项目选定技术栈的惯例，同类文件保持一致。
- 组件输入、事件、默认值和禁用条件应含义清楚。
- 复杂状态明确列出可用状态与转换，避免互相矛盾的布尔值。
- 把页面数据请求和纯展示逻辑适当分开，避免组件隐式依赖全局配置。
- 对外分发前明确公开接口与内部实现，不随意暴露内部文件路径。

## 3. 样式

- 以 [DESIGN.md](../DESIGN.md) 为视觉基线，定稿后集中维护设计令牌。
- 优先复用项目已有样式与组件，避免引入多套重复的基础控件。
- 补齐默认、悬停、焦点、禁用、忙碌和错误状态。
- 使用长标题、多行说明、窄屏与缩放检查布局。
- 图标使用选定资源或图标库，不能代替必要的文本标签。

## 4. 数据与交互

- 模拟数据独立管理，明确标注演示状态。
- 主操作有真实行为，只有实现了保存、复制、下载等操作才能反馈成功。
- 空内容、请求失败和处理中都应有明确反馈。
- 表单提交先校验输入，失败时保留用户已经填写的内容。
- 外部内容按所选框架提供的安全方式渲染，不直接注入不受信任的 HTML。

## 5. 依赖

新增依赖应有具体用途，并确认项目现有能力是否足够。版本写入真实依赖清单与锁文件，避免同时维护多种包管理器锁文件。

当前依赖清单为 frontend/package.json，锁文件为 frontend/pnpm-lock.yaml。使用 Phosphor React 图标、系统字体与普通 CSS；设计变量位于 src/app/globals.css，布局位于 workspace.css，用户新选聊天布局的工作区令牌与覆盖样式集中在 chat-layout.css。

2026-10-28：工作区按最新参考使用本地 DM Sans 与系统中文回退，字体文件和 OFL 许可位于 frontend/public/fonts；字体声明、18px 主标签 / 14px 辅助文字、手机 16px 主标签与统一字重在 chat-layout.css 集中维护。账号页与登录页沿用原有样式，工作区账号导航使用工作区字体变量。

## 6. 无障碍

处方流程使用 prescription-dialog / prescription-fields / prescription-report 分离编排、编辑和结果展示，类型与请求集中在 prescription-api.ts，样式集中在 prescription.css。multipart 上传由浏览器生成 Content-Type boundary，不能手动设置 JSON Content-Type。编辑任意已确认字段须清除确认勾选；更换处方清空旧数据，关闭弹窗释放 Object URL 并恢复焦点。报告复制保留类别、依据和复核边界。

- 用语义化按钮、链接和表单表达操作。
- 输入有可见标签，错误提示关联到对应控件。
- 图标按钮有可理解名称，焦点样式清楚可见。
- 弹窗和抽屉处理焦点进入、关闭与返回。
- 主要流程可通过键盘完成，不只依赖拖拽或鼠标悬停。
- 状态同时使用文字或图标，避免只通过颜色区分。
- 图片提供适当替代文本，动画尊重系统减少动画设置。

## 7. 示例与验证

每个重要组件应检查正常、空内容、长内容、忙碌和错误状态。对复杂行为增加必要测试，浏览器中核验键盘操作与响应式布局。

组件站中的示例应与实际组件同步。若示例依赖尚未实现的接口，明确展示其演示性质。

独立发布时还需满足 [REGISTRY.md](REGISTRY.md) 的登记和校验要求。


## 后端与账号组件约定（2026-10-27）

Python 位于 backend/app，文件和函数采用 snake_case；配置、数据库、密码 / 权限、输入模型与 HTTP 接口分开。新增后端依赖维护 requirements.txt、requirements-dev.txt 与 requirements-lock.txt。

前端页面只负责组装 Authenticated 与业务组件；API 及账号类型集中在 src/lib/api.ts。后端最终校验权限，前端根据权限调整按钮和入口。账号样式在 auth.css；共享资料的 stored 字段与示例 demo 字段分别表示持久化和演示，不将二者混淆。

处方口径通过 `PrescriptionDoseScope` 复用上传 / 核对控件，纯转换 `withDoseScope` 集中维护整方选择。默认每剂量遵循用户明确要求，单味修改主动切换逐味模式；禁止只删除 finding 而不更新后端检查数据。

处方审核结论由后端 `review.py` 生成，`narrative.py` 将当前处方与 findings 转为固定五节 `sections`；`PrescriptionReport` 和复制函数共同消费该结构，不在客户端推断临床内容。旧格式报告自动重查，缺少完整五节的异常响应明确报错并保留可编辑数据。

表单 data-field 与服务端 missing_information.field 一致；补充入口通过现有弹窗的确认步骤定位字段，不新增弹窗或丢弃已核对值。报告重查和复制继续消费同一 sections；清单只包含实际缺失项。
