# RAG 耗时诊断与提速验收

日期：2026-11-01。本机仍使用今天接入的 Qwen3-Embedding-0.6B + FAISS，未恢复旧关键词 RAG。仅做本地验证，未主动向 DeepSeek 发送问题或知识库片段。

## 本次结论

读取用户已发起请求的后端阶段日志，得到：

| 阶段 | 耗时 |
| --- | --- |
| 读取资料 | 0.015 秒 |
| 上下文整理 | 0.003 秒 |
| 本地检索，含冷启动 | 62.420 秒 |
| DeepSeek 生成 | 2.899 秒 |
| 请求总计 | 65.492 秒 |

这次约 95% 的耗时在本地检索，生成模型不是这条请求的主要瓶颈。本机 i5-10200H、8 GB 内存；原后端进程私有内存约 4108 MB，同时观察到可用物理内存不足和大量换页。原先延迟初始化将模型导入、权重加载和首次推理都放在首条提问内，重复查询缓存无法解决新进程的首问。

## 已部署的调整

- CPU 保留当前检查点的原始 BF16 权重，逐层 Linear / Embedding / 归一化以 FP32 计算；不让整份 FP32 权重常驻。`EMBEDDING_CPU_STORAGE=fp32` 可用于对照。
- `RAG_WARMUP=true` 默认在服务启动阶段准备索引、加载模型并执行一次真实本地嵌入，完成后才提供 API。初始化开销移至启动阶段，并未消失；终端显示 `Local vector RAG ready` / `Application startup complete` 后再使用，不需重复启动。
- 保持同一模型、查询指令、分块、归一化与 222 片段 FAISS 索引。完整 8 位量化未通过一致性检查，未部署；未启用 ONNX 替代模型，也未重建原索引。
- 保留查询向量 LRU 128 条、按账号隔离的已校验回答缓存 16 条 / 120 秒、追问先理解再检索、`use_cache=false` 以及分阶段计时。

## 本地实测与当前服务

新存储方式在同一进程连续检索三个不同问题，不调用云端：

| 场景 | 本地检索时间 | 最高相似度 / 首个来源 |
| --- | --- | --- |
| 新进程首条「可以理气健脾、燥湿化痰的药有哪些」，包含初始化 | 63.069 秒 | 0.651772 / 陈皮 |
| 随后的新问题「陈皮和青皮有什么区别」 | 3.623 秒 | 0.657587 / 陈皮 |
| 随后的新问题「黄芪怎么炮制成饮片」 | 0.701 秒 | 0.572009 / 黄芪 |

三类结果与原 FP32 模式对应记录一致。后两条没有命中相同问题缓存。计时只覆盖本地检索，不能等同于完整 AI 回答，也不是保证每条新问题固定低于 4 秒。证据保存在本机忽略目录 `backend/.qa/rag-compact-cpu-benchmark.json`。

当前服务进程已完成预热并通过 `/api/health`：

- 启动阶段共 48.24 秒；其中模型构造阶段日志为导入 6.27 秒、分词器 1.17 秒、权重 3.39 秒，总计 10.82 秒。启动总时长还包含 FAISS / 资料准备和首次推理。
- 服务进程私有内存约 2986 MB，工作集约 897 MB，低于优化前私有内存约 4108 MB。私有内存与物理工作集为不同指标，不将其混为可用内存。独立基准脚本的内存计数无效，已移除该字段；上述数值来自 Windows Get-Process。
- 原索引清单最后修改时间仍为 2026-11-01 14:45:17；直接复用原索引，没有用实验量化向量覆盖它。

## 验证和边界

- 后端全量回归 115 项通过；新增同构小型 Qwen 的数值一致性测试，覆盖左侧 padding、BF16 权重、FP32 输出和与整模型 FP32 的结果比较；使用本地随机权重，不下载模型。
- 本次只调整后端运行与启动方式，没有改页面布局；未重复浏览器验收。此前前端类型检查、31 项回归和本地浏览器流程通过，见其他验收记录。
- 尚未主动进行真实云端问答联调，遵守用户仅本地验证的选择。2.899 秒来自用户已有请求的日志，不能作为新配置下整体响应速度的承诺。
- 服务重新启动仍有一次性准备时间；本机内存紧张、长时间空闲后的换页、复杂追问的额外理解请求及云端速度仍会影响体验。流式输出尚未接入。
